## Issues Identified (inputs for Steps 2–5)

1. **Two duplicate `printifyFetch` clients** — `listing` and `fulfillment` both define the function locally with near-identical logic. → Fix in Step 2.
2. **`Content-Type` missing `;charset=utf-8`** — both clients. → Fix in Step 2.
3. **No `User-Agent` header** — both clients. Printify's docs require it. → Fix in Step 2.
4. **429 not handled** — both clients bail immediately on any 4xx including 429. Printify returns 429 on rate-limit overage; without special handling the call fails permanently. → Fix in Step 2.
5. **No publishing rate limiter** — `listing`'s `printifyFetch` has no Bottleneck at all; `fulfillment`'s limiter is sized for global only. The 200/30-min publishing ceiling on `POST /products` and `PUT /products/{id}` is currently unenforced. → Fix in Step 2.
6. **No `external_id` on order create** — idempotency relies solely on the human-readable `label` field, not Printify's documented `external_id` mechanism. → Fix in Step 3.
7. **Order status is polled** — `tracking-poller.ts` polls `GET /orders/{id}` every 30 min. Printify offers webhooks for `order:shipment:created` that would eliminate most of this polling. → Fix in Step 4.
8. **No error-rate guard** — no instrumentation to detect when our 4xx/5xx rate approaches Printify's 5% account-enforcement threshold. → Fix in Step 5.
